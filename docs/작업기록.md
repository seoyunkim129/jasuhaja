## 🛠 새로 붙인 기능

### 1. 시설을 목록으로 관리

전에는 `수영장`, `다이소`가 코드에 박혀 있었다. 목록으로 바꿔서 나중에 사용자가 직접 추가할 수 있게 했다.

```js
const 기본시설 = [
  { 이름:'수영장', 색:'#3FD8C4', 그림:'수영'   },
  { 이름:'다이소', 색:'#F5A623', 그림:'쇼핑백' }
];
```

### 2. 아이콘 핀 마커

그림 파일을 따로 두지 않고 SVG를 글자로 만들어 쓴다 (data URI). Vercel에 올릴 때 챙길 파일이 안 늘어난다.

- 물방울 핀 + **흰 테두리** (마커끼리 겹쳐도 경계가 보임)
- 흰 배경 동그라미 (그림이 핀 색에 안 묻힘)
- 그림이 있으면 그림, 없으면 **앞글자** (`GS25` → `GS`, `스타벅스` → `스`)

### 3. 시설을 직접 추가 (이번 기획 변경의 핵심)

필터 바 아래 입력칸에 `GS25`를 넣으면 파란 핀에 `GS`가 찍힌다. `스타벅스`를 넣으면 보라 핀에 `스`.

- `localStorage`에 저장돼서 **새로고침해도 남는다**
- 기본 시설(수영장·다이소)은 못 빼고, 추가한 것만 `×`로 뺀다
- **6개 제한** — 시설이 늘면 지도를 열 때마다 그 수만큼 TMAP에 물어보게 된다

### 4. 네이버 지도 링크

핀을 누르면 네이버 지도로 이어진다. **리뷰·길찾기·영업시간을 네이버가 다 보여준다.**

```js
https://map.naver.com/p/search/{시설이름 + 구이름}
```

API 키가 필요 없다. 이것 하나로 **우리가 도보 시간을 계산할 이유가 사라졌다.**

### 5. 회색 점 289개 숨기기

시설을 4개 넣어보니 지도가 점으로 꽉 찼다. 조건 미달 단지 289개가 화면을 덮어 정작 봐야 할 시설이 안 보였다.

```
기본        조건 통과 단지만 (299 → 10개)
체크박스    "조건 미달 단지도 흐리게 보기"로 다시 볼 수 있음
```

데이터가 사라진 게 아니라는 걸 화면에 밝혀두는 게 중요했다.

### 6. 범례가 스스로 따라오게

범례 HTML에 색을 또 적지 않고, **지도 마커와 똑같은 함수**로 그린다. 그래서 시설을 추가하면 범례도 저절로 늘어나고, 마커와 범례가 어긋날 수가 없다.

### 7. 두 화면을 오갈 수 있게

`index.html`에 `map.html`로 가는 링크가 **하나도 없었다.** 주소창에 직접 쳐야만 지도에 들어갈 수 있었다. 세 곳에 달았다.

### 8. 수영장이 아닌 것 걸러내기

TMAP "수영장" 분류에 수영할 수 없는 곳이 잔뜩 섞여 나왔다.

```js
const 유아전용 = /키즈|어린이|유아|아동|주니어|차일드|kids/i;
const 미개장   = /공사중|오픈예정|개장예정|준비중/;
const 물놀이장 = /물놀이장|워터파크/;
const 법인명   = /주식회사|㈜|\(주\)/;
```

지도 마커 수영장 **29곳 → 19곳**.

## 🧱 막힌 것 / 어떻게 풀었나

### ⓪ 색이 겹치는 버그

시설을 추가할 때 색을 **순서대로** 물려줬더니, 하나 지웠다 새로 넣으면 색이 겹쳤다 (스타벅스와 CU가 둘 다 보라).

```js
저장.push({ 색: 추가색[저장.length % 추가색.length] })   // 겹침
저장.push({ 색: 남은색(저장) })                          // 안 쓰는 색을 고름
```

> **배운 것** — "순서대로 주기"는 지우기가 없을 때만 맞다. 지울 수 있으면 "안 쓰는 걸 고르기"로 가야 한다.

### ① 스킬의 프록시 서버가 죽어 있었다

```
https://k-skill-proxy.nomadamas.org  →  HTTP 530
```

**해결** — 스킬 안의 파이썬 코드를 읽어보니 프록시를 안 거치고 국토부에 직접 붙는 방법이 있었다. **API 키도 필요 없었다.** 이 방식을 강서·양천만으로 좁혀서 다시 만들었다.

> **배운 것** — 스킬이 안 돌아가도 그 안의 코드를 읽으면 우회로가 보인다. 스킬은 블랙박스가 아니라 그냥 읽을 수 있는 파일 묶음이다.

### ② 화면이 계속 옛 데이터를 보여줬다

CSV를 바꿨는데 화면이 안 바뀌었다. 원인이 **두 개 겹쳐** 있었다.

1. **브라우저 캐시** — 서버는 새 CSV를 주는데 브라우저가 옛 파일을 들고 있었다
2. **`.catch`가 모든 오류를 삼켰다** — `fetch(...).then(데이터담기).catch(() => 데이터담기(예비데이터))` 는 `데이터담기` 안의 오류까지 잡아서, 화면이 조용히 옛 데이터로 돌아가도 아무도 몰랐다

**해결**

```js
fetch(CSV주소, { cache: "no-cache" })            // 매번 "바뀌었나요?" 물어봄
  .then(r => r.ok ? r.text() : Promise.reject(new Error("HTTP " + r.status)))
  .catch(오류 => { console.warn(...); return 예비데이터; })   // 못 읽었을 때만
  .then(데이터담기);
```

```
HTTP 429 QUOTA_EXCEEDED
```

762개 단지 × 2 = 1,524번이 필요한데 하루 한도가 약 1,000건이었다. **480개까지만 채워지고 멈췄다.**

**진짜 해결** — 도보 시간을 우리가 계산하지 않기로 했다. 네이버 지도 링크로 넘기면 네이버가 길찾기를 해준다. **문제 자체가 사라졌다.**

### ④ 지도 API 3사 비교 (중요)

## 🔧 코드 정리 (기능 변화 없음)

`index.html`(목록 화면)과 `map.html`(지도 화면)이 완전히 다른 파일인데,
필터 조건을 판단하는 `조건통과()`와 `시간바꾸기()` 함수가 **글자 하나 안 틀리고 똑같이** 두 파일에 복사돼 있었다.

나중에 조건을 하나 바꿀 때 한쪽만 고치고 다른 쪽을 깜빡하면, 목록 화면과 지도 화면이 서로 다른 기준으로 단지를 보여주는 눈에 안 띄는 버그가 생길 수 있었다.

**해결** — `공통.js` 파일 하나로 합쳐서 두 화면이 같이 불러쓴다.

```html
<script src="papaparse..."></script>
<script src="공통.js"></script>   ← 새로 추가
```

`다시그리기()`는 화면마다 그리는 방식이 완전히 달라서 (카드 vs 지도 마커) 각자 파일에 그대로 뒀다. **똑같은 코드만** 합쳤다.

### 과정

   - Vercel의 환경 변수(`TMAP_KEY`)에서 값을 읽어와, 배포할 때마다 그 파일을 새로 만들도록 했다
3. Vercel에서 깃허브 저장소 Import → `TMAP_KEY` 환경 변수 등록 → Deploy
4. 확인: 앱키 정상 주입, 지도·데이터 파일 전부 정상, GS25 같은 사용자 추가 시설도 실제 배포본에서 작동 확인

### 막힌 것

**① 배포 직후 URL이 로그인 화면으로 튕겼다**

Vercel이 만든 임시 배포 URL(`mulddae-bwbm0zol4-...`)이 `vercel.com/sso-api`로 리다이렉트됐다. 원인을 찾아보니 이건 **버그가 아니라 Vercel의 기본 배포 보호 기능**이었다. 그런데 실제로는 그 URL이 아니라 프로젝트의 정식 도메인(`mulddae-cyan.vercel.app`)이 따로 있었고, 거긴 처음부터 정상이었다.

> **배운 것** — Vercel이 배포 직후 보여주는 URL이 항상 최종 주소는 아니다. Domains 탭에서 진짜 주소를 확인해야 한다.

**② `공통.js`가 curl로는 404였다**

`curl`로 확인하니 한글 파일명(`공통.js`)이 404였다. 그런데 이건 curl이 한글을 인코딩 안 하고 그대로 보내서 생긴 착시였다. **실제 브라우저는 `공통.js`를 `%EA%B3%B5%ED%86%B5.js`로 자동 변환해서 요청**하기 때문에 진짜 사용자한텐 문제가 없었다.

> **배운 것** — 도구로 확인한 결과가 항상 사용자가 겪는 것과 같지 않다. 도구의 한계인지 실제 버그인지 구분해야 한다.

### 오늘 하려던 것

네이버에서 발급받은 Client ID와 Client Secret으로 수영장 관련 카페 후기 검색 결과를 가져올 준비를 한다.

### ✅ 여기까지 됐다

- `.env.local`을 Git에서 제외하도록 `.gitignore`를 고쳤다.
- 실제 값을 넣지 않는 견본 파일 `.env.example`을 만들었다.
- `api/cafe-search.js`를 추가했다.
- 브라우저가 네이버를 직접 부르지 않고, **Vercel 서버 함수가 비밀키를 붙여 대신 호출**한다.
- 결과에서는 제목·요약·카페명·원문 링크만 골라 보낸다.
- 같은 검색어는 1시간 보관해 네이버 API 호출 수를 아낀다.
- `node --check api/cafe-search.js` 문법 검사를 통과했다.

### 🛠 새로 붙인 기능

```text
map.html
   ↓ /api/cafe-search?q=마포아트센터 수영장 자유수영 후기
Vercel 서버 함수
   ↓ Client ID·Secret을 서버에서만 붙임
네이버 카페글 검색 API
```

### 🧱 막힌 것 / 어떻게 풀었나

**문제** — Client Secret을 `map.html`이나 JavaScript에 넣으면 방문자 누구나 볼 수 있다.

**해결** — 키를 Vercel 환경변수에만 저장하고, `/api/cafe-search`가 네이버 API를 중계하도록 했다. 브라우저에는 비밀키가 전달되지 않는다.

> **배운 것** — 브라우저에서 실행되는 HTML·JavaScript에는 이름이 `secret`인 값을 숨길 수 없다. 비밀값이 필요한 호출은 서버를 한 번 거쳐야 한다.

### ➡️ 다음에 할 것

1. 로컬 `.env.local`과 Vercel에 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` 등록
2. 실제 검색 요청 1회 시험
3. `마포아트센터 수영장 자유수영 후기` 등 검색어별 결과 품질 비교
4. 결과가 쓸 만할 때만 지도 정보창에 후기 목록 UI 추가

### 🧱 첫 실제 호출에서 막힌 것 — 구형 API와 API HUB의 차이

처음 코드는 예전 네이버 개발자센터 문서를 따라 아래 주소와 헤더를 썼다.

```text
https://openapi.naver.com/v1/search/cafearticle.json
X-Naver-Client-Id / X-Naver-Client-Secret
```

하지만 이번에 발급받은 것은 **NAVER API HUB 키**다. 이 키를 예전 주소에 보내면 키가 정확해도 `401 / Authentication failed`가 난다.

공식 이관 문서를 다시 찾아 현재 방식으로 수정했다.

```text
https://naverapihub.apigw.ntruss.com/search/v1/cafearticle
X-NCP-APIGW-API-KEY-ID / X-NCP-APIGW-API-KEY
```

> **배운 것** — 이름이 똑같이 Client ID·Secret이어도, 어느 발급처에서 받은 키인지에 따라 주소와 헤더가 다르다. 최신 플랫폼에서 발급받았다면 최신 플랫폼의 문서를 확인해야 한다.

### ✅ 실제 배포 확인

검색어:

```text
마포아트센터 수영장 자유수영 후기
```

결과:

- 전체 검색 결과 148건
- API가 한 번에 10건을 정상 반환
- 상위 결과에 `마포아트센터 수영장 수강신청(+자유수영 시간표)`, `마포아트센터 수영장 후기`, `용산 마포 일대 수영장 자수후기`가 포함됨
- 다른 수영장 후기처럼 덜 관련된 글도 섞여 있어, 화면에 붙이기 전 **수영장 이름이 제목·요약에 실제로 들어간 결과를 우선하는 정리 규칙**이 필요함

로컬 직접 호출과 Vercel 배포 주소의 `/api/cafe-search` 호출을 모두 확인했다. 비밀키는 응답과 Git에 포함되지 않았다.

- 네이버 카페 검색 결과의 제목·요약문에서 혼잡 관련 표현과 샤워실·락커 관련 표현을 찾아 별도 칸에 표시한다.
- 후기에서 근거를 찾지 못하면 내용을 만들지 않고 `검색 요약문에서 확인되지 않음`으로 표시한다.
- 원문 링크는 요약 아래에 근거 자료로 유지한다.

### 🏷 정보 상태 문구 정정

`방문 전 전화 확인`은 시설 자체가 불확실하다는 뜻으로 읽힐 수 있어 `공식 시간표 미확인`으로 바꿨다. 자유수영 가능 여부는 확인했지만, 최신 시간과 가격을 운영처의 공식 페이지에서 확정하지 못한 시설에만 이 상태를 사용한다.

### ⭐ 후기 기반 항목별 별점

- 혼잡 여유도, 시설 쾌적도, 수영 환경, 가성비를 각각 다른 검색어로 조회한다.
- 각 항목에서 긍정·부정 표현이 포함된 서로 다른 후기만 점수 계산에 사용한다.
- 관련 후기 3개 이상일 때만 1~5점 별점을 표시한다.
- 관련 후기 1~2개는 `평가 보류`로 표시해 작은 표본으로 점수를 만들지 않는다.
- 점수와 함께 사용된 후기 수와 대표 근거 문장을 표시한다.
- 항목별 검색 결과를 합치고 같은 링크는 한 번만 원문 목록에 보여준다.
- 다른 수영장 글에 시설명이 우연히 언급된 경우를 막기 위해 시설명이 제목에 포함된 글만 평가에 사용한다.

별점은 시설의 공식 평가가 아니라 네이버 카페 검색 요약문에서 감지한 후기 신호다. 검색 API가 원문 전체를 제공하지 않는 한 이 한계를 화면에 계속 밝혀야 한다.

### 📚 검색 표본 확대

처음 후기 API는 네이버 검색 기본값과 같은 10개만 받아왔다. 시설명이 제목에 들어간 글과 평가 표현이 있는 글을 다시 거르면 항목별로 0~2개밖에 남지 않아 대부분 `평가 보류`가 됐다.

NAVER API HUB 공식 문서에서 `display`가 요청당 최대 100개까지 가능하고, 하루 호출 한도는 25,000회임을 확인했다. 호출 횟수는 늘리지 않고 검색어별 결과만 10개에서 100개로 확대했다. 화면에는 여전히 중복을 제거한 원문 최대 12개만 보여준다.

처음에는 `시설명 + 사람 혼잡 레인`처럼 평가 단어를 검색어에 직접 넣었지만, 실제 사용자가 쓰는 자연스러운 후기 제목과 맞지 않아 결과가 지나치게 적었다. 검색과 평가를 분리해 `시설명 + 자유수영 후기`, `시설명 + 자수 후기`, `시설명 + 수영장 후기`로 글을 넓게 받은 뒤, 가져온 제목·요약문 안에서 혼잡·시설·수영 환경·가격 표현을 분류하도록 바꿨다.

## 🏊 웹캠 수영 게임 — 1단계 (웹캠 + 포즈 인식)

물때로 사람을 데려오는 "미끼"를 만들기로 했다. 검색창을 먼저 보여주는 대신 **"업무시간에도 수영해볼까요?"** 로 게임을 먼저 권하고, 게임이 끝난 화면에서 `map.html`(자유수영 지도)로 보낸다.

새 파일 `수영게임.html` 하나만 추가했다. 기존 코드는 건드리지 않았다. 빌드 도구·npm·프레임워크 없이 CDN 스크립트만 쓴다.

### 쓰는 도구 (실제 주소 확인함, 모두 HTTP 200)

| 용도 | 주소 | 크기 |
|---|---|---|
| 포즈 인식 라이브러리 | `cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@1.0.1/vision_bundle.mjs` | 155KB |
| WASM 폴더 | `.../@mediapipe/tasks-vision@1.0.1/wasm` | - |
| 모델 | `.../pose_landmarker/pose_landmarker_lite/float16/1/pose_landmarker_lite.task` | 5.8MB |

버전을 `@latest`로 고정하지 않고 `1.0.1`로 못박았다. CDN이 새 버전을 올려서 갑자기 동작이 바뀌는 걸 막는다.

### 1단계에서 한 일

- 웹캠 영상을 띄우고, 그 위에 같은 크기 canvas를 겹쳐 어깨(11·12)·팔꿈치(13·14)·손목(15·16)을 점으로 찍는다.
- FPS와 각 관절의 정규화 y좌표(0=화면 맨 위, 1=맨 아래)를 숫자로 표시한다.
- 좌우를 뒤집어(거울) 보여준다. 웹캠이 안 뒤집히면 손을 왼쪽으로 뻗었는데 화면에선 오른쪽으로 가서 조작이 안 된다. 대신 MediaPipe의 좌우 번호는 해부학 기준이라, 화면 라벨과 맞추려고 코드에서 11↔12처럼 번호를 바꿔 넣었다.
- 같은 영상 프레임을 두 번 넣으면 MediaPipe가 오류를 내므로 `currentTime`이 바뀔 때만 인식을 돌린다.
- 카메라 거부와 모델 로딩 실패를 각각 사람이 읽을 수 있는 한국어 문장으로 화면에 띄운다.

### 실행 방법

카메라는 `file://`로 열면 브라우저가 아예 차단한다. 반드시 로컬 서버로 띄워야 한다.

```
python -m http.server 8000
```
→ `http://localhost:8000/수영게임.html`

> **배운 것** — 웹캠·마이크 같은 민감한 장치는 브라우저가 `localhost`나 `https`에서만 허용한다. 파일을 더블클릭해서 열면 코드가 맞아도 절대 안 된다.

## 🏊 웹캠 수영 게임 — 2단계 (스트로크 판정)

1단계에서 FPS 17이 나왔고, 손을 들었을 때 손목 y가 어깨 y보다 확실히 작아지는 것을 확인했다. 판정의 기준이 되는 신호가 충분히 뚜렷하다는 뜻이라 2단계로 넘어갔다.

### 판정 원리

```
높이 = 어깨y − 손목y
```

y좌표는 화면 위로 갈수록 작아진다. 그래서 손을 들면 이 값이 +로 커지고, 내리면 −가 된다. 관절의 절대 위치 대신 **어깨와의 차이**를 쓴 이유는, 사람이 카메라에 가까이 오거나 멀어져도 기준이 흔들리지 않게 하기 위해서다.

1. 높이가 `올라감 기준`을 넘으면 → 상태 `UP`
2. `UP`인 상태에서 높이가 `내려감 기준` 아래로 떨어지면 → 스트로크 1회

### 떨림을 막는 두 장치

**히스테리시스** — 올라가는 문턱(0.06)과 내려오는 문턱(0.00)을 다른 값으로 뒀다. 두 문턱이 같으면 손이 그 근처에 머무를 때 미세한 흔들림만으로 UP/DOWN이 수십 번 반복되어 카운터가 폭주한다. 올라갈 때와 내려올 때의 문턱을 벌려두면 한 번 올라간 손은 문턱을 한참 지나 내려와야만 다시 세어진다.

**쿨다운** — 마지막으로 센 뒤 최소 간격(300ms)이 지나야 다음 걸 센다. 히스테리시스를 통과하는 빠른 떨림에 대한 2차 방어선이다.

### 화면에 넣은 것

- 왼팔/오른팔 횟수와 총합, 각 팔의 현재 상태(UP/DOWN) 배지
- 각 팔의 현재 "높이" 숫자 — 임계값을 얼마로 둬야 할지 눈으로 보고 정하라고 넣었다
- 어깨 높이에 흰 점선 — 손목이 이 선을 넘나드는 게 판정의 전부라는 걸 보이게 했다
- 올라감/내려감 기준과 최소 간격을 실시간으로 바꾸는 슬라이더 3개

임계값을 코드에 박지 않고 슬라이더로 뺀 이유는, 사람마다 팔 길이와 카메라 거리가 달라서 **정답 숫자가 하나로 정해지지 않기** 때문이다. 직접 저어보면서 맞추는 게 빠르다.

판정 로직은 `스트로크판정()` 함수 하나에 모아뒀다. 이 함수는 화면이나 카메라를 전혀 모르고 숫자만 받아서 숫자만 돌려준다. 그래서 이 함수만 읽고 고치면 판정 방식 전체를 바꿀 수 있다.

> **배운 것** — 센서 신호로 "동작 1회"를 세는 일은 문턱값 하나로는 안 된다. 사람의 움직임에는 항상 떨림이 섞여 있어서, 올라갈 때와 내려올 때의 기준을 분리하고 시간 간격까지 둬야 비로소 숫자가 맞는다.

## 📏 후기 분석의 기준표 만들기 (정답표)

### 왜 이걸 먼저 했나

키워드 방식과 트랜스포머 방식 중 뭐가 나은지 비교하려고 했는데, **비교할 자가 없었다.** 두 방식의 결과를 나란히 놓아도 "어느 쪽이 맞았는지"를 판정할 근거가 없으면 비교가 성립하지 않는다. 그래서 AI를 붙이기 전에 사람이 읽고 매긴 정답표부터 만들었다.

### 1) 표본 고정 — `scripts/후기표본만들기.mjs`

네이버 검색 결과는 날마다 달라진다. 오늘 15건이던 후기가 내일 12건이 되면, 두 방식의 점수 차이가 방식 때문인지 데이터 때문인지 구분할 수 없다. 그래서 한 시점의 후기를 `analysis/gold/후기표본.json`에 박아두고, 이후 모든 측정은 이 파일만 본다.

수영장 6곳 × 검색어 3종 = 18회 호출 → 원본 574건 → 제목에 시설명이 포함된 글만 68건 → 링크 중복 제거 **37건**.

### 2) 사람 판정 — `scripts/정답표만들기.py`

37건을 전부 읽고 네 항목(혼잡 여유도 / 시설 쾌적도 / 수영 환경 / 가성비)에 `긍정·중립·부정·관련없음`을 붙였다. 판단 근거 문구도 함께 남겨서, 나중에 왜 그렇게 봤는지 따질 수 있게 했다.

혼잡 항목은 방향을 명시했다. **긍정 = 여유롭다, 부정 = 붐빈다.** 점수가 높다는 게 "사람이 많다"가 되면 사용자가 정반대로 읽는다.

결과: 37건 중 평가 내용이 있는 판정은 **17건**뿐이었다. 나머지는 수강신청 요령, 훈련 일지, 번개 모임 후기처럼 시설 평가가 아예 없는 글이었다. 카페 글의 대부분은 후기가 아니라는 뜻이다.

### 3) 키워드 방식 채점 — `scripts/정확도측정.py`

| 항목 | 정답 | 키워드가 찾음 | 적중 | 오탐 | 누락 | 정밀도 | 재현율 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 혼잡 여유도 | 5 | 3 | 2 | 1 | 3 | 67% | 40% |
| 시설 쾌적도 | 7 | 0 | 0 | 0 | 7 | — | **0%** |
| 수영 환경 | 2 | 2 | 2 | 0 | 0 | 100% | 100% |
| 가성비 | 3 | 2 | 2 | 0 | 1 | 100% | 67% |
| **합계** | **17** | **7** | **6** | **1** | **11** | **86%** | **35%** |

**찾아낸 건 대체로 맞지만(86%), 있어야 할 것의 3분의 1밖에 못 찾는다(35%).**

가장 심한 건 시설 쾌적도로, **7건을 전부 놓쳤다.** 원인은 키워드 목록이 `샤워실이 깨끗`처럼 너무 긴 통문장이라는 데 있었다. 실제 후기는 `정말 깨끗해졌어요`, `시설도 깔끔한`, `시설과 프로그램의 균형`처럼 쓴다. 글자가 한 칸만 달라도 규칙이 걸리지 않는다.

오탐 1건은 예상대로 마포아트센터 **한식뷔페 글**이었다. `가는 길이 복잡하다`의 `복잡`을 혼잡도 부정으로 세었다. 사람은 한 문장만 읽어도 이게 길찾기 이야기인 걸 아는데, 단어만 보는 규칙은 구분하지 못한다.

### 이 측정이 바꾼 판단

원래는 "키워드는 기준선이고 트랜스포머가 더 나을 것"이라는 가정이었다. 측정해보니 문제의 성격이 달랐다.

- 키워드가 **틀린 말을 하는 게 아니라, 말을 안 한다.** 정밀도 86% / 재현율 35%.
- 따라서 개선 방향은 "더 똑똑한 판정"이 아니라 **"표현의 폭을 넓히는 것"** 이다.
- 이건 트랜스포머가 실제로 잘하는 일이라, 비교 실험의 가설이 더 선명해졌다. 가설: *재현율이 35%에서 얼마나 오르는가, 그 대가로 정밀도 86%를 얼마나 잃는가.*

> **배운 것** — 정확도를 재기 전까지는 어디를 고쳐야 할지 알 수 없다. 숫자를 보기 전 내 짐작은 "오탐이 문제"였는데, 실제 문제는 누락이었다. 측정 없이 AI를 붙였다면 잘못된 곳을 고쳤을 것이다.

## 🔍 후기 데이터 출처를 다시 찾다

### 문제를 발견한 계기

정답표 문서에 "네이버 검색 API는 카페 본문을 주지 않는다"는 설명을 한 줄 적어뒀는데, 사용자가 그 문장에서 멈췄다. **"그럼 판정하는 게 저 세 줄에 대한 분석이 다냐"**는 질문이었다. 맞는 지적이었고, 그 한 줄이 프로젝트의 근간을 흔드는 문제라는 걸 충분히 강조하지 않은 것이 잘못이었다.

### 실제로 재본 네이버 API 응답

API 응답 100건의 길이를 직접 측정했다.

| 항목 | 길이 |
| --- | --- |
| 제목 | 71자 |
| 요약문 | 평균 142자 (최소 81 / 최대 211) |
| 링크 | 48자 |

요약문은 거의 전부 앞뒤가 `...`로 잘려 있다. 원문이 3000자여도 우리에게 오는 건 142자다. 검색 결과 미리보기용으로 만들어진 값이라 그렇다.

**따라서 별점 시스템은 분석 방식을 바꿔도 성립하지 않는다.** 데이터 자체가 없기 때문이다. 37건 중 시설별로 근거 3건을 넘긴 칸은 24칸 중 1칸뿐이었던 것도 이 때문이다.

### 본문을 가져올 수는 없나

없다. robots.txt를 직접 확인했다.

- **네이버 카페**: 전면 `Disallow: /` + AI·RAG 목적 접근 금지 명시
- **네이버 블로그**: 같은 금지 문구에 더해 `User-agent: ClaudeBot / Disallow: /`로 특정 명시

기술적으로 가능한지와 별개로, 이용약관 위반의 위험은 서비스를 운영하는 쪽이 진다. 포트폴리오에 "크롤링했다"고 적을 수도 없다.

### 대안: 구글 지도 리뷰

직접 확인한 결과, 구글 지도 리뷰는 **잘리지 않은 본문에 별점까지 붙어서** 나온다.

| 수영장 | 평점 | 리뷰 수 | 구글 분류 |
| --- | ---: | ---: | --- |
| 아현스포렉스 | 4.0 | 168 | 수영장 |
| 월드컵스파랜드24 | 3.5 | 149 | 스파 (수영장 태그 12) |
| 창천교육문화회관 수영장 | 3.8 | 13 | 수영장 |
| 마포아트센터 | 4.3 | 1,406 | 문화센터 (체육 30) |
| 신석스포렉스 | 2.0 | 1 | 체육관 |
| 소의체육문화센터 | — | 구글 지도 미등록 | — |

아현스포렉스의 한 리뷰는 시설 부정과 가성비 부정을 근거 문장까지 갖춰 담고 있었다. 네이버 142자로는 얻을 수 없는 밀도다. 글마다 붙은 별점은 사람이 직접 매긴 라벨이라, 분석 결과를 검증할 기준으로도 쓸 수 있다.

### 확인한 제약 세 가지

공식 문서로 확인했고, 설계에 그대로 반영해야 한다.

1. **API는 시설당 최대 5개만 반환한다.** 화면에 168개가 보여도 프로그램이 받는 건 5개다. Places API 문서에 `A maximum of 5 reviews can be returned`로 명시돼 있다. 리뷰 데이터의 대량 수집을 막으려는 의도로 보인다.
2. **리뷰 본문은 저장·캐시가 금지된다.** Place ID만 무기한 저장할 수 있고 나머지는 보관할 수 없다. 네이버 표본처럼 파일로 고정해두는 방식을 쓸 수 없으므로, 필요할 때마다 호출하는 구조여야 한다.
3. **비용은 사실상 0원이다.** 리뷰 항목은 Enterprise 등급이고 월 1,000회가 무료다. 수영장 6곳이면 6회다. 다만 결제수단 등록은 필요하다.

### 남은 판단

수영장 6곳 중 구글에서 쓸 만한 곳은 3곳(아현·월드컵·창천)이고, 여기서 얻는 온전한 리뷰는 15건이다. 네이버에서 얻은 37건이 전부 142자로 잘려 있고 그중 평가 내용이 있는 건 17건이었던 것과 비교하면, 건수는 줄지만 분석 가능한 분량은 늘어난다.

두 출처를 대체 관계가 아니라 역할 분담으로 쓰는 안을 검토 중이다. 구글은 분석할 본문, 네이버는 원문 링크 목록.

> **배운 것** — 데이터 출처의 한계는 프로젝트 시작 전에 확인해야 한다. "API로 가져올 수 있다"와 "쓸 만한 내용이 온다"는 전혀 다른 말이다. 응답을 한 번만 열어봤으면 몇 주 일찍 알았을 문제였다.

- **결정 기록** — 사용자가 내린 판단과 그 판단이 바꾼 결과
- **검증한 순간** — AI 말을 그대로 받지 않고 되묻거나 직접 확인한 기록
- **AI가 틀린 것** — 무엇을 잘못 말했고 어떻게 드러났는지
- **잘 통한 프롬프트 전문** — 요약하지 않고 그대로
- **숫자와 출처 파일**
- **제약 안에서 한 설계 결정**

채용하는 쪽이 보는 건 "AI를 썼는가"가 아니라 "AI를 쓰면서도 판단은 본인이 했는가"다. 그 증거는 완성된 코드가 아니라 과정 기록에 남는다. 몰아서 쓰면 기억이 날아가므로 그때그때 채운다.

## 🧹 죽은 코드 정리와 공휴일 표시 버그 수정

### 죽은 코드 제거

`공통.js`와 `danji.csv`를 지웠다. 둘 다 아파트 단지를 찾던 시절의 코드로, 다이소·수영장 도보권 필터와 단지 299곳 데이터가 들어 있었다. 프로젝트 방향이 자유수영장 찾기로 바뀌면서 쓰이지 않게 됐는데 파일만 남아 있었다.

지우기 전에 전체 검색으로 확인했다. 어느 HTML도 `공통.js`를 불러오지 않고, `조건통과`·`시간바꾸기`·`가격숫자` 같은 함수 이름도 다른 파일에 없었다. `danji.csv`를 읽는 코드도 없었다.

남겨두면 다음에 이 폴더를 여는 사람이 "단지 필터가 아직 동작하나" 하고 읽어보게 된다. 안 쓰는 코드는 읽는 사람의 시간을 뺏는다.

### 공휴일이 사라지는 문제를 보다가 진짜 버그를 찾았다

시간표의 요일구분을 플래너 칸으로 바꾸는 함수는 이렇게 생겨 있었다.

```js
if (v.includes('평일') || v.includes('월~금')) return 월~금 + (토 있으면 토);
return ['월','화','수','목','금','토','일'].filter(d => v.includes(d));
```

`공휴일`이 어느 칸에도 안 나온다는 게 원래 확인하려던 문제였다. 그런데 실제 데이터 6종을 전부 대입해보니 그보다 큰 문제가 있었다.

| 요일구분 | 고치기 전 | 고친 후 |
| --- | --- | --- |
| `월~금` | 월화수목금 | 월화수목금 |
| `토` | 토 | 토 |
| `평일` | 월화수목금 | 월화수목금 |
| `평일·토` | 월화수목금토 | 월화수목금토 |
| `일·공휴일` | 일 | 일 **공휴일** |
| `토·공휴일` | **토 일** ← 버그 | 토 **공휴일** |

**`공휴일`이라는 낱말 안에 `일` 글자가 들어 있다.** 그래서 `'토·공휴일'.includes('일')`이 참이 되고, 토요일 회차가 일요일 칸에도 표시됐다. 월드컵스파랜드24의 `토·공휴일 10:00~19:30` 한 줄이 실제로 일요일에 잘못 떠 있었다. 일요일에 문 여는 줄 알고 찾아갔으면 헛걸음이다.

`평일`에도 같은 함정이 있다. 지금은 `평일`이 앞 분기에서 걸러져 문제가 안 되지만, 분기 순서가 바뀌면 바로 터진다.

수정 방법은 **요일 글자를 찾기 전에 낱말부터 떼어내는 것**이다.

```js
const 낱요일 = 표기.replace(/공휴일/g,'').replace(/평일/g,'').replace(/월~금/g,'');
```

이렇게 하면 `토·공휴일`은 `토·`만 남아 토요일에만 걸리고, 공휴일은 따로 붙인다. 플래너도 7칸에서 8칸으로 늘려 공휴일 칸을 만들었다.

### 검증

로컬 서버를 띄우고 브라우저에서 두 시설의 상세 화면을 직접 열어 확인했다.

- 월드컵스파랜드24: 일요일 칸이 비었고, 공휴일 칸에 `10:00–19:30`이 들어감
- 마포아트센터: 일요일과 공휴일에 각각 3회차씩 정상 표시

> **배운 것** — 한국어 낱말에는 다른 낱말이 통째로 들어 있는 경우가 많다. `공휴일` 안의 `일`, `평일` 안의 `일`처럼. 글자 포함 여부(`includes`)로 판정하면 이런 데서 조용히 틀린다. 그리고 이 버그는 "공휴일이 안 보인다"를 고치려다 우연히 찾은 게 아니라, **실제 데이터를 전부 대입해 표로 만들어봤기 때문에** 드러났다.

## 🔑 구글 리뷰 연결 (서버 함수)

### Place ID만 저장하고 리뷰는 매번 받는다

구글 정책을 문서로 확인한 결과, 저장 규칙이 항목마다 다르다.

| 항목 | 저장 |
| --- | --- |
| Place ID | **무기한 가능** (캐시 제한에서 명시적으로 제외됨) |
| 좌표 | 최대 30일 |
| 리뷰 본문·평점 | **불가** |

그래서 Place ID만 `수영장.csv`에 저장하고, 리뷰는 볼 때마다 새로 받는 구조로 만들었다. ID를 저장해두면 매번 이름으로 검색하지 않아도 되므로 API 호출이 절반으로 줄고, 엉뚱한 장소를 집을 위험도 사라진다. 응답에는 `Cache-Control: no-store`를 붙여 중간 서버가 보관하지 않도록 했다.

### Place ID를 채우다 발견한 것

`scripts/구글장소ID채우기.mjs`로 6곳을 조회했더니 5곳은 정확히 잡혔는데, **소의체육문화센터가 `서울소의초등학교`로 잡혔다.** 주소가 같은 다른 장소다. 이름과 주소로 검색하면 이런 일이 생긴다.

결과를 확인하지 않고 그대로 저장했다면, 화면에는 수영장 정보 밑에 초등학교 리뷰가 붙었을 것이다. 자동으로 채운 값은 반드시 사람이 한 번 읽어야 한다는 걸 다시 확인했다. 해당 ID는 지우고 비고에 사유를 남겼다.

### 작성자 표기는 의무다

정책 문서에 이렇게 적혀 있다.

> 사진이나 리뷰를 표시할 때는 항상 작성자를 표시해야 합니다. 각 리뷰에는 작성자 아바타, 이름, 프로필 링크가 포함됩니다.

여기에 더해 원본 리뷰로 이동할 수 있는 링크와 `Google Maps` 표기도 요구된다. 처음 만든 시안에는 이 부분이 빠져 있었다. 서버 함수가 `authorAttribution`과 `googleMapsUri`를 그대로 내려보내도록 했고, 화면에서도 반드시 함께 표시해야 한다.

이 제약은 화면 설계에도 영향을 준다. 원래 시안은 항목별로 근거 문장만 뽑아 보여주는 형태였는데, 작성자와 원본 링크가 각 인용마다 따라붙어야 한다.

### 만든 것

- `api/google-reviews.js` — 브라우저가 구글을 직접 부르지 않도록 중계한다. 키는 환경변수에만 있고 응답에 포함되지 않는다. Place ID 형식을 정규식으로 검사하고, 할당량 초과(429)는 따로 구분해 안내한다.
- `scripts/구글장소ID채우기.mjs` — Place ID를 한 번만 채운다. 이미 있으면 건너뛴다.
- `수영장.csv`에 `구글PlaceID`, `구글확인일` 칸 추가. 구글이 12개월보다 오래된 ID는 갱신을 권장하므로 확인일을 함께 남긴다.

### 검증

Vercel 없이 함수만 직접 호출해 확인했다. 정상 요청은 200에 리뷰 5개와 작성자 정보가 모두 왔고, `Cache-Control: no-store`가 붙었으며, 응답에 API 키가 섞이지 않았다. `placeId`가 없거나 형식이 틀리면 400으로 막혔다.

> **배운 것** — 외부 데이터를 쓸 때는 "받을 수 있는가"만이 아니라 "저장해도 되는가", "표시할 때 무엇을 함께 보여야 하는가"까지 확인해야 한다. 이 세 가지가 각각 다른 규칙을 따른다.

## ⏱ 기간 기준을 1년으로 낮추다

### 3년에는 근거가 없었다

사용자가 물었다. **"시설 근데 3년으로 정한 이유가 따로 있어? 리뷰란에 넣을 기간이 없어서 그런 거야?"**

정확한 지적이었다. 3년은 구글 리뷰 5개만 쓰던 시절에 정한 값이다. 그때 아현스포렉스는 1년 이내 후기가 0개라 기간을 좁히면 화면이 비었다. 그래서 임의로 넓혀뒀는데, **네이버 블로그를 붙이면서 전제가 바뀐 뒤에도 옛 숫자가 그대로 남아 있었다.**

### 재보고 정했다

주제별로 1년 안에 남는 문장 수를 실제로 셌다.

| 수영장 | 혼잡 | 시설 | 물 |
| --- | ---: | ---: | ---: |
| 아현스포렉스 | 4 | 6 | 5 |
| 마포아트센터 | 14 | 24 | 4 |
| 창천교육문화관 | 3 | 13 | 4 |
| 월드컵스파랜드24 | 0 | 2 | 0 |

화면에는 주제당 3개만 보여주므로 네 곳 중 세 곳은 1년으로도 남아돈다. 월드컵스파랜드24는 구글에 찜질방으로 등록된 곳이라 원래부터 얇다.

### 규칙을 한 곳으로 모았다

전에는 주제마다 최대 나이를 따로 박아뒀다. 혼잡 3년, 기타 3년, 시설·물 무제한. 값이 흩어져 있으면 어디를 고쳐야 할지 알기 어렵고 사용자가 화면에서 바꿀 수도 없다. 주제별 값을 모두 없애고 **기간 버튼 하나로 통일**했다. 기본값은 1년이고 2년·3년·전체로 넓힐 수 있다.

### 날짜 없는 카페글을 어떻게 할 것인가

네이버 카페글은 작성 날짜가 오지 않는다. 기간으로 거르려면 판단이 필요했다.

아현스포렉스 혼잡 항목의 1년 이내 네 건은 **전부 날짜 없는 카페글**이다. 이를 제외하면 0건이 되는데, 그 네 건이 실제로 가장 쓸모 있는 문답이다. `sort=date`로 받아온 글이라 최근일 가능성이 높지만 증명할 수는 없다.

포함하되 화면에 `날짜 없음`을 갈색으로 표시해 사용자가 판단하게 했다. 감추는 것보다 밝히는 쪽이 낫다.

> **배운 것** — 기준값은 정할 때의 전제와 함께 기억해야 한다. 전제가 바뀌면 값도 다시 봐야 하는데, 코드에 박힌 숫자는 왜 그 값인지를 말해주지 않는다. 그래서 이번에는 값을 코드에서 빼내 화면 버튼으로 올렸다.

### 정원을 어떻게 쓸 것인가 — 용도를 바꿨다

처음에는 `정원 ÷ 레인수`로 혼잡도를 숫자화하려 했다. 사용자가 반박했다. **"정원이 크다고 해서 꼭 그만큼 인원이 온다는 보장이 없다."** 맞는 지적이다. 정원은 상한일 뿐 실제 방문객 수가 아니다.

그래서 용도를 바꿨다. 정원이 확실하게 말해주는 것은 **"헛걸음할 수 있다"** 이다.

- 정원이 정해져 있음 → 늦게 가면 못 들어감
- 발권 시간이 따로 있음 → 그 시간에 맞춰 가야 함

양천구민체육센터는 회차마다 정원이 45~100명으로 다르고, **발권 시간이 이용 시간과 별도로 공지된다.** 16:00 회차는 15:40~16:10에 발권한다. 이건 방문 전에 반드시 알아야 할 정보인데 어느 후기에도 정리돼 있지 않았다.

`자유수영시간.csv`에 `정원명`과 `발권시간` 칸을 추가하고, 상세 화면에 `⚠ 입장 전 확인` 상자로 띄웠다. 플래너의 시간 칩에도 정원을 함께 적는다.

> 혼잡 예측으로 쓰면 틀린 정보가 되지만, 입장 실패 경고로 쓰면 정확한 정보가 된다. **같은 데이터라도 무엇이라고 부르느냐에 따라 맞기도 하고 틀리기도 한다.**

### 요일 표기에서 조심한 것

신월문화체육센터 시간표에는 `월~토`로 적힌 회차가 있다. 그대로 넣으면 안 된다. 화면의 `적용칸()`은 `월~금`만 범위로 다루고 나머지는 글자 포함으로 판정하므로, `월~토`는 **월요일과 토요일만** 표시된다.

이미 쓰고 있던 `평일·토`로 바꿔 넣었다. CSV에 값을 넣기 전에 화면 함수에 대입해 결과를 확인하는 절차를 거쳤다.

### 자치구 필터

버튼 목록을 코드에 박지 않고 `수영장.csv`의 `자치구` 값에서 만든다. 구가 하나뿐이면 버튼 줄 자체를 감춘다. 구를 추가할 때 코드를 고치지 않아도 된다.

### 검증

브라우저에서 직접 확인했다. 자치구 버튼 `전체 9 · 마포구 6 · 양천구 3`, 양천구 선택 시 3곳, `양천구 + 오늘 가능`(토요일) 3곳. 상세 화면의 입장 경고는 *"회차마다 정원 45명부터 있어요"*, *"16:00 회차는 15:40~16:10에 발권합니다"* 로 나왔다.

작업 중 새로 만든 `.warn` 클래스가 기존 배지의 `.warn`과 이름이 겹쳐 스타일이 섞였다. `.entry-warn`으로 바꿨다.

## 🔎 양천구 민간·시립 수영장 2곳 추가

사용자가 알려줬다. **"양천구에 수영장 더 있어. 내가 아는데만 해도 미진수영장 있어."** 맞았다. 구시설관리공단 사이트만 보면 공단이 운영하는 시설만 나오고, 민간·시립 수영장은 빠진다.

### 찾는 방법을 바꿨다

구글 지도에서 `미진수영장`, `양천구 수영장`, `신정동 수영장`, `목동 수영장`, `신월동 수영장`으로 검색하고 주소가 양천구인 것만 모았다. 27곳이 나왔다.

여기서 성인 자유수영이 되는 곳을 가려야 하는데, 구글 분류만으로는 알 수 없었다.

| 곳 | 구글 분류 | 판정 |
| --- | --- | --- |
| 미진수영장 | 수영장 | **포함** |
| 시립목동청소년센터 | 관공서 | **포함** (분류만 보면 놓쳤을 곳) |
| 블루라군수영장(3곳) | 학교·체육학교 | 제외 (어린이 대상) |
| 오션키즈·국가대표어린이수영클럽·키즈팰리스 | 수영장·체육학교 | 제외 (어린이 전용) |
| 안양천 물놀이장·서서울호수공원 물놀이장 | 수영장·놀이터 | 제외 (야외 물놀이장) |
| 청학스포츠타운·서울YMCA 양천지회 | 스포츠 단지·협회 | 제외 |

판정은 구글 분류가 아니라 **네이버 블로그에서 `시설명 + 자유수영`을 검색해 글이 있는지**로 했다. 청학스포츠타운과 YMCA는 0건이라 뺐고, 미진수영장은 30건, 시립목동청소년센터는 10건이 나왔다.

### 확인한 것과 못한 것을 나눴다

**미진수영장** — 공식 홈페이지를 찾지 못했다. 후기에서 자유수영 8,000원, 이용 제한 시간 없음, 공휴일에도 운영한다는 내용을 여럿 확인했지만 시간표는 없다. `정보상태=후기참고`로 넣고 방문 전 전화 확인이 필요하다고 적었다.

**시립목동청소년센터** — 구 목동청소년수련관이다. 공식 사이트(`wawa.or.kr`)의 페이지 19개를 훑어 `자유수영`이 들어간 페이지 2개를 찾았다. 자유수영 운영과 발권 안내는 공식으로 확인됐고, 공지에 `화목 14:00 자유수영`도 적혀 있었다. 다만 **전체 시간표가 표가 아니라 공지글 안에 흩어져 있어** 확보하지 못했다. 평일 20:00~20:50, 4,500원은 후기 기준이다.

두 곳 모두 억지로 채우지 않고 출처와 상태를 그대로 적었다.

### 화면에서 고친 것

공지에는 시작 시간만 적혀 있고 종료 시간이 없는 회차가 있다(`화목 14:00`). `시간텍스트()`가 `14:00–`처럼 뒤에 줄표만 남기고 끝나서, 종료 시간이 없으면 `14:00~`으로 표시하도록 고쳤다.

> **배운 것** — 시설 목록을 한 출처에서만 모으면 그 출처가 가진 것만 보인다. 구시설관리공단은 공단 시설만, 구글 검색은 분류가 제각각이다. **사용자가 아는 것을 물어보는 게 가장 빨랐다.**

## 📍 마포·양천에서 멈추고, 위치·시간 추천으로 전환

> 이후 사용자 검토에서 현재 위치는 두 구만 다루는 단계에는 과하다고 판단해 제거했다. 아래는 첫 번째 시안 기록이며, 현재 화면은 다음 절의 `구 + 날짜 + 시간` 검색을 사용한다.

사용자가 자치구를 계속 늘리는 것보다 **마포구와 양천구의 정보를 먼저 완성하고, 실제로 갈 곳을 고르는 기능이 더 중요하다**고 방향을 정했다. 이에 목록 위에 `내가 갈 시간에 가까운 곳 찾기`를 추가했다.

### 추천 기준

1. 사용자가 고른 날짜의 요일과 자유수영 시간표를 맞춘다.
2. 시작·종료 시간이 모두 있고 선택 시간이 그 사이면 `시간표상 이용 가능`으로 판정한다.
3. 요일 정보는 있지만 시간이 비어 있으면 가능하다고 단정하지 않고 `시간 확인 필요`로 둔다.
4. 이용 가능한 회차를 먼저 놓고, 같은 상태 안에서는 현재 위치와의 직선거리 순으로 정렬한다.

위치 정보는 버튼을 누를 때 브라우저에서 한 번 받아 거리 계산에만 쓰며 서버나 파일에 저장하지 않는다. 도보시간 API는 이전에 일일 한도가 소진됐으므로 이번 최소판에서는 직선거리라고 정확히 표시했다.

### 검증

- JavaScript 문법 검사 통과
- 로컬 브라우저에서 날짜·시간 입력, 위치 버튼, 자치구 필터, 수영장 12곳 렌더링 확인
- 테스트 브라우저가 위치를 제공하지 않는 경우 사람이 읽을 수 있는 오류 안내가 나오고 버튼이 다시 활성화되는 것 확인
- 날짜·시간을 바꾸면 추천이 다시 계산되도록 연결
- 위치 계산과 운영 판정은 브라우저 안에서만 수행

실제 위치 권한을 허용한 성공 경로는 사용자의 일반 브라우저에서 한 번 더 확인해야 한다.

## 🏊 게임 3단계 — 레이스

웹캠 앞에서 팔을 저으면 캐릭터가 레인을 나아가고, 상대보다 먼저 결승선에 닿으면 이긴다. 2단계의 `스트로크판정()`은 그대로 두고 그 위에 레이스를 얹었다.

### 속도 규칙

```
스트로크 1회 → 속도 += 추진력
매 순간       → 속도 -= 속도 × 저항 × 시간    (안 저으면 멈춤)
위치          += 속도 × 시간
```

왼팔·오른팔을 번갈아 저으면 추진력에 1.35를 곱한다. 한 팔만 빠르게 흔드는 치팅을 막기 위한 장치다.

### 난이도를 짐작으로 정하지 않았다

처음에 상대 완주 시간을 45초로 뒀는데, 브라우저 없이 물리 계산만 따로 돌려보니 **느리게 저어도(0.7회/초) 이겼다.** 요구사항은 "열심히 저으면 이기고 대충 저으면 진다"였으므로 맞지 않았다.

상대 완주 시간을 30·32·35초로 바꿔가며 다시 계산했다.

| 저는 방식 | 기록 | 상대 32초 기준 |
| --- | ---: | --- |
| 빠르게 번갈아 1.2회/초 | 21.3초 | 이김 |
| 보통 번갈아 1.0회/초 | 25.5초 | 이김 |
| **보통 한팔만 1.0회/초** | 32.0초 | **짐** |
| 느리게 0.7회/초 | 32.0초 | 짐 |
| 대충 0.5회/초 | 32.0초 | 짐 |

32초가 맞았다. 번갈아 저으면 이기고, 같은 속도로 한 팔만 흔들면 진다. **치팅 방지가 숫자로 확인된다.** 이 표를 코드 주석에 남겨 다음에 난이도를 만질 때 근거가 되게 했다.

웹캠 없이 물리만 따로 돌린 덕분에 카메라 앞에서 팔을 수십 번 젓지 않고도 난이도를 맞출 수 있었다.

### 유입 연결

결과 화면 아래에 `주변 자유수영장 보기` 버튼이 나온다. 게임이 끝난 직후가 "실제로 수영하러 갈까"라는 마음이 가장 큰 순간이라 그때 지도로 연결한다. 이것이 처음부터 게임을 만든 이유다.

## 🐛 map에 함수를 그대로 넘겨 생긴 요청 오류

게임 화면을 확인하다 네트워크 기록에서 이상한 요청을 발견했다.

```
/api/naver-search?q=...&sort=1&type=마포아트센터 수영장 자유수영 후기,마포아트센터 수영장 자수 후기,...
                        ^^^^^^ 숫자      ^^^^ 검색어 배열 전체
```

원인은 이 한 줄이었다.

```js
검색어들.map(검색요청)
```

**`배열.map(함수)`는 함수에 (값, 순번, 배열) 세 개를 넘긴다.** 검색요청의 두 번째 인자가 정렬, 세 번째가 종류였으므로 순번이 정렬로, 배열 전체가 종류로 들어갔다.

`검색요청`에 인자를 추가할 때 이 호출부를 함께 고치지 않아서 생긴 문제다. 서버가 잘못된 값을 무시하고 기본값으로 떨어뜨려 화면은 멀쩡해 보였고, 그래서 오래 드러나지 않았다.

```js
검색어들.map(q => 검색요청(q))
```

필요한 인자만 주도록 감쌌다.

> **배운 것** — 함수 시그니처를 바꾸면 호출부를 전부 찾아봐야 한다. 특히 `map`, `forEach`, `then`처럼 **함수를 그대로 넘기는 자리**는 인자가 몇 개 들어가는지 눈에 보이지 않는다. 그리고 이 버그는 화면이 아니라 **네트워크 기록**을 봤기 때문에 드러났다.

## 🎨 게임 4단계 — 판정 보강·비주얼·결과 공유

### 스트로크가 실제보다 많이 세어진 문제

사용자가 **19번 저었는데 화면에는 29번(왼 15 / 오른 14)** 으로 찍혔다고 알려줬다.

원래 규칙은 이랬다.

```
높이가 올라감(0.06)을 넘으면 → UP
UP에서 내려감(0.00) 아래로 떨어지면 → 1회
```

이 규칙은 **팔을 조금 까딱한 것과 크게 한 바퀴 돌린 것을 구분하지 못한다.** 0.06은 화면 높이의 6%밖에 안 되고, 손목 좌표는 매 프레임 조금씩 떨린다. 문턱 근처에서 떨면 한 번 저은 것이 두세 번으로 세어진다.

**최소 진폭**을 넣었다. UP 동안의 최고 높이를 기억했다가, 그 값이 기준(기본 0.15)을 넘을 때만 센다.

### 재현해보고 고쳤다

짐작으로 고치지 않으려고 브라우저 없이 판정 함수만 떼어 돌렸다.

깨끗한 팔 동작(위 +0.30 ~ 아래 −0.30)에서는 **어떤 설정을 써도 10회가 정확히 10회로 나왔다.** 흔들림을 ±0.20까지 키워도 마찬가지였다. 중복이 재현되지 않았다.

재현된 것은 **팔이 어깨선 근처에서 머뭇거릴 때**였다.

| 손목 흔들림 | 고치기 전 | 고친 후 | (정답 10회) |
| --- | ---: | ---: | --- |
| ±0.10 | 10.5회 | 9.6회 | |
| ±0.14 | 12.1회 | 9.7회 | |

즉 최소 진폭은 **머뭇거림으로 생기는 중복**을 막는다. 다만 사용자에게 실제로 일어난 일이 이것인지는 확인하지 못했다. 원격으로는 알 수 없다.

그래서 **판정 간격을 화면에 찍게 했다.** 최근 10회의 간격이 `980ms · 1020ms · 140ms …` 처럼 나오는데, 100~200ms짜리가 섞여 있으면 한 번 저은 걸 두 번 센 것이다. 이 숫자가 있어야 원인을 말할 수 있다.

> 고치는 것보다 **무엇이 잘못됐는지 보이게 만드는 것**이 먼저다. 숫자가 안 맞는다는 말만으로는 어디를 고쳐야 할지 알 수 없다.

### 비주얼

사용자가 참고 화면을 보내줬다. 실제 수영 영상에 웹캠이 구석에 붙은 형태였다.

- 위에서 내려다본 사람 — 머리·수모·몸통·양팔. **팔이 스트로크 위상에 맞춰 돌아간다.** 앞으로 뻗을 때 길어지고 물을 저을 때 각도가 바뀐다
- 물결을 사인파로 그리고, 바닥 타일선이 뒤로 흐른다. **속도가 붙으면 빨리 흘러 속도감이 난다**
- 레인 로프를 부표 구슬로 그리고 흰색·주황색을 번갈아 칠했다
- 스트로크마다 물보라가 튄다
- 웹캠을 우상단에 작게 띄워 내 팔 동작이 보이게 했다
- 결승선은 체크무늬

### 결과 공유

**인스타그램은 웹에서 스토리에 바로 올리는 공식 방법을 제공하지 않는다.** 앱끼리 주고받는 방식만 있고 웹 페이지에서는 쓸 수 없다.

그래서 할 수 있는 만큼만 했다.

1. 결과 카드를 1080×1920(스토리 비율) 이미지로 그린다 — 승패·기록·스트로크 수·경기 화면
2. 휴대폰이면 공유창을 띄운다. 거기서 인스타그램을 고르면 된다
3. 공유창을 못 쓰면 파일로 내려받고, 직접 올리라고 안내한다

"바로 업로드"라고 적지 않고 실제로 되는 것만 적었다.
